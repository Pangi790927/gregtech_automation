## What is already there to build on

- **virt_composer's coroutines** (`../utils`, not edited from here): a Lua script runs as a
  `lua_coro_t`; a C function that cannot answer yet returns `lua_await`, which suspends the script
  while a colib task on the pool does the work, and resumes it with the answer. homeauto runs its
  whole control this way. So Lua says `local reply = link:send(robot, "status_fast")`, and waits
  without a thread of its own.
- **The simulator** (`simulator/`, C++ on virt_composer): a world of cells, rendering, Minecraft's
  textures, and OpenComputers machines running the mod's own `machine.lua`. It has no robot
  component yet (`computer.isRobot` answers false). `scenes/draw3d` is today's viewer.
- **The relay link in C++:** `console/connector.h` and `protocol.h`, which `term.exe` uses - the
  pipe and zones of `01-protocol.md`, with no Python.

## Decided: a new 3d-draw program that borrows the simulator's composers

The user, 2026-10-05: "new 3d-draw program, borrow the simulator's composers (maybe include them
or build upon them?)". One exe in `3d-draw/`, laid out like math_writer (below), that holds the
world, plans, simulates, drives the robots and shows it all; the simulator stays what
`simulator/OBJECTIVE.md` says it is.

**Include as they are, never copied:** `render_composer.h` (the 3D view), `world_composer.h` (the
cells it draws), `mc_assets.h` (Minecraft's textures from the user's install), `gl_util.h`,
`imgui_composer.h`, `path_composer.h` - read 2026-10-05, they need nothing of the simulator but
each other and `../utils`. **Build upon:** 3d-draw's own composers hold what the simulator has
no use for - the site (the map in chunks, the layers, the plan), the pathfinder, the link - and
fill a `world_composer` with what is to be shown. A change one of the shared headers needs is
made in `simulator/`, and the simulator's own tests (`main.exe --test`) must still pass.

## No threads, anywhere, to start with

The user, 2026-10-05: "try first no threads anywhere, I think we don't need it, but if
pathfinding ever needs it (look up how thco works in utils for a way to give "pathing requests"
to a thread pool and get the answer back in the async pool)". Everything runs on colib's one
thread: C++ coroutines for the link and the files, Lua coroutines for the logic.

If pathfinding ever needs a thread: `../utils/thco.h` is the way back - a worker thread pushes
its answer into `thco_t2c_queue_t`, which wakes a coroutine through a pipe (`co::read` on the
pipe's end). Read 2026-10-05: it opens the pipe with `pipe2(..., O_CLOEXEC)`, which Windows
does not have, so on this PC it would need a Windows form from `../utils` - asked of the user
then, not worked around (CLAUDE.md, rule 5).

## C++: only what must be fast or touches the machine

| Part | Does |
|---|---|
| world | the cells in chunks, the palette, the built and fixed layers; reading and writing the chunk files; queries for Lua (a cell, a box, a column's top) |
| pathfinder | ways through known air for many robots at once: paths may share cells and time, never a cell another will dig; a request in, a path out |
| link | one channel per robot through the relay (`console/connector.h`): `exec`, `give_way`, `geo`, `status_fast`, `status`, `history`, each awaitable from Lua |
| viewer | the simulator's rendering, and every drawing primitive: lines, boxes, outlined cells, coloured cubes, markers, labels - Lua says what, C++ draws it |

**The C++ API is meant to close.** The user, 2026-10-05: "also drawing lines and things like this
should stay in c++ and the result beeing that only the lua side will change after the api is
somehow complete, the mathwriter's imgui connectors and the one from the simulator should help
with that". The panels and controls come through the ImGui composers (the simulator's
`imgui_composer.h`, math_writer's); once world, paths, link and drawing are exposed, new work is
Lua only.

## Lua: everything else (coroutines on the one thread)

The user, 2026-10-05: placing "will I guess be part of the lua side, same as craft, me, read_me,
and probably the rest too". So the knowledge and the decisions are Lua, as data and small
functions:

| Lua module | From | Holds |
|---|---|---|
| blocks | placing.py | how each block is placed and read back: stairs, slabs, ladders, leaves, logs, doors; item of a block; substitutes |
| recipes | craft.py | Gunter's recipes and how the grid is filled |
| me | me.py, read_me.py | the mini ME's computer, the interface's sides, the stock |
| planner | buildsite.py | dig and place packets on the 5x5x8 grid, their order, the proof, scaffolding (05) |
| programs | builders.py | a packet into `exec` programs: the printer's pattern, exceptions, palette, `$cost` (04) |
| robot | sim.py | the robot copy: runs a program's ops on the world, with `blocks` for what a `put` leaves, ticks and energy - the same rules the planner used |
| crew | builders.py | one coroutine per robot (send, poll, compare, `history` on a difference); which robot takes which packet; `give_way` |
| scouts | survey.py, name.py | `geo`, exploring, naming; the rules (sky or a named tree, never break ground) |
| map | zones.py, keep_chunks.py | merging a scout's map, the work zone, over the C++ world |
| designs | design/*.py | the plans, written as Lua: changed in the exe and seen at once |

**The viewer talks to all of it directly.** The viewer is the simulator's Lua already
(`scenes/draw3d/controller.lua`); in the same exe it reads the crew's own tables - the robot
copies, the packets and their state, the markers - instead of files re-read once a second
(`live.log`, `pending-*.txt`). What the control knows, the user sees, the moment it knows it.

## Testing without the game

- The robot side: the robot's Lua (the state machine and the notation's parser) runs inside the
  simulator's OC machines once they have a robot component - the same code as in the game.
- The whole exe: run with every robot a copy and no relay - a build start to finish, every
  packet, zero stops and zero divergences. That replaces today's gate (`tests/gate.py`), as
  3d-draw's own `tests/lua/*.lua`, run the way math_writer runs its tests.

## Files on disk, kept as they are

Chunks, plans, `built.txt`, `fixed.txt`, markers: the formats stay, so the move is gradual and
the old tools can still read them while they last.
