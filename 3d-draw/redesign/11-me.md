## 3a: the ME on the link, robots at the interface

The user, 2026-10-05: "the exe(windows side) keeps a view inside the me, it puts gunter to craft
all needed subparts and lets the rest run, gunther will craft things with exec practically, the
whole 8 slots (1 left to give items back) will be given to one robot, such that it can take all
needed items and craft or go build, in one go, the computer gets the request from the pc,
executes, wakes pc, pc sends exec to robot and so on" - and: "if the exe knows there are 200
planks and the robot needs to take 180 planks then the computer simply sets the planks in the
interface and the robot takes 18- planks, afterwards the exe tells the computer to clear the
interface, this way this is finished in 3 commands".

- **The exe's view of the ME** (`scripts/me.lua`): read once when linked (`items`), then kept by
  the exe itself - a take subtracts, a give adds, a craft both. Nothing is asked before a trip.
- **The ME's computer** (`robot/me_machine.lua`, the old me_server.lua in the robots'
  conversation, `<id> ok 0 <value>`): no logic, a thin hand on the interface. One command a
  request: `config <slot> <name> <meta> <size> | <slot> - ...`, every slot set or cleared in one
  line; its answer wakes the exe. And `items`, `count`. It cannot see the interface's slots (OC
  1.8.0.13's DriverBlockInterface reads none) - it need not: the exe knows the counts.
- **The interface, one robot at a time:** slots 1-8 stocked for it, a stack each; 9 never stocked,
  for giving back - with every slot not stocked at the time (the interface hands what is in an
  unstocked slot to the network on its tick).
- **A tick between `config` and the takes:** a slot (re)configured fills on the interface's
  next tick; a robot one step away (Gunter's park) took 0 of 14. The exe waits the tick
  (1.5 s) before it sends the exec with the takes.
- **The robot takes only when told, only what is there** (the user, 2026-10-05: "the bot should
  only take after it was told to, so there is nothing to retry"). A short take is a stop, a
  divergence: the counts are the exe's, so a wrong one is to be seen, not tried again.
- **Give into a slot** (`g<dir><mine>.<their>[*n]`, inventory_controller.dropIntoSlot): a plain
  drop lands in a stocked slot. One stack a free slot.
- **Its slots:** the robot's status names how many it has (`slots <n>`).

## A packet's trip: three commands, then the way back

1. To the ME's computer: `config` - the packet's items into slots 1-8 (and the last robot's
   slots cleared, the same line).
2. To the robot, one `exec`: to the interface (west side, 0 0 1 facing east), the takes, and the
   packet from there. Gunter's crafting is the same: takes, `c` ops, no packet.
3. To the ME's computer: `config` clearing them - merged with the next request when there is one.
4. To the robot, one `exec` once its packet is done: back to the interface, what it dug and what
   is left given into the free slots, then home to its park (10-live.md).

A robot holding more than its tools when it sets off gives that back first, the same way. A
packet needing more than 8 stacks waits for a second round (open). The copies' world holds the
interface stocked as configured, its free slots taking all, so every program dry-runs first.
