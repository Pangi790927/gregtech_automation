== RULES LEARNED (the hard way) ==
1. Each reactor has 2 input hatches, 1 fluid each -> ONE recipe at a time per reactor.
2. Fixed sides: input A always NORTH, input B always SOUTH. Never split a fluid over both
   buffers (that jammed MK3: Pu ended in both hatches).
3. Exact amounts = whole runs. Next recipe only after both buffers drained.
   Leftover of one input in a hatch blocks every other recipe -> manual emptying.
4. Stall guard: if buffers do not go down for ~30 s, stop that reactor and report.
5. Timeouts: count real loop steps, not uptime (server lag makes game time slow).
   Always switch reactors off + clear interface config at the end, also on error.
6. Start energy (40M-500M EU) is paid when a reactor starts; during continuous operation
   the cost is only EU/t. -> BIG BATCHES per start (player, 2026-10-01).
7. Interface tanks hold only 16000 L per slot: for a big batch, feed in several transfers,
   all of A to NORTH, all of B to SOUTH (buffers 256000 L), reactor stays on.

== ENERGY MEASUREMENT (Titanium x4 on MK2, 2026-10-01, after player's energy update) ==
- Running Parallel = 85 (not 128): parallels are sized to the hatch capacity (85 x 49152 x2 ~ 8.4M EU/t).
- Real supply is lower: running drains stored EU 320M -> 0 in ~6 s, then the reactor STOPS.
  Each cycle makes ~24,480 L Ti (2 x 85 x 144). Recharge 0 -> full in ~3 s (~6.5M EU/t in).
- It does NOT restart by itself: setWorkAllowed(false) then (true) restarts it (works).
- No separate start cost seen: the stored EU is a working buffer; start value = minimum charge.
- So the limit is EU supply rate, not start energy. Balancer must: restart when inactive with
  EU full and inputs still in the hatches (track made vs expected = runs x out).
- Server lag: loops with os.sleep(1) take ~3 s real per step; keep each oc_lua call short
  (<= ~40 steps) or run the balancer as its own program on the computer.
- Left at end of session: ~24,480 L each Al + F in MK2 hatches (finishes with one more restart).

== ALLOCATION MODEL (player, 2026-10-01; replaces RES) ==
priority = projected level (lowest first). RESERVED (#): stock taken for a recipe, gone for others,
kept until scheduled. DESIRED (!): one missing input per recipe; blocks lower priorities from
reserving/starting with it; incoming stock goes to the desirer first; ends when complete (then it
may desire its other input); never touches others' reservations. Schedulable = both inputs fully
reserved (batch size = larger reactor's). Repeats (x4) only from free, undesired stock.
No deadlock: recipes only wait for supply, never for each other. Screen: PRIORITY list.
Spike labels: 'start from idle (gap)' when the reactor was idle the second before. A repeat batch that starts after the reactor went idle is gated like a switch (EU full).
